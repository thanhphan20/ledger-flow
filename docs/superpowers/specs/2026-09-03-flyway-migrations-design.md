# Flyway Migrations Design

Status: approved
Date: 2026-09-03

## Summary

Replace `ddl-auto: update` with Flyway across all three services (payment-service, ledger-service, loan-service). Each service gets a `V1__init.sql` migration matching its current JPA entities, `ddl-auto: validate`, and `baseline-on-migrate: true` so existing databases (built by ddl-auto) are baselined without collision. Test suites also run Flyway against H2 `MODE=PostgreSQL` for full schema parity.

## Goals

- Migration-authored schema as the single source of truth.
- Same schema in dev, CI, compose, prod, and test runs.
- Fail-fast at boot if schema drifts (validate).
- No manual DDL; `mvn clean install` produces a migration-ready JAR.

## Non-goals

- No Liquibase — Flyway's SQL-first approach is the de facto Spring Boot standard.
- No Testcontainers — H2 with `MODE=PostgreSQL` is sufficient for this repo's test scope.
- No rollback support — Flyway's philosophy is forward-only; rollbacks are new migrations.
- No per-environment migration variants — single migration set for all environments.

## Per-service migrations

### payment-service (`src/main/resources/db/migration/V1__init.sql`)

```sql
CREATE TABLE payments (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id BIGINT,
  amount NUMERIC(38, 2),
  currency VARCHAR(255),
  status VARCHAR(255),
  reference_id VARCHAR(255),
  idempotency_key VARCHAR(255),
  created_at TIMESTAMP
);
CREATE UNIQUE INDEX uk_payments_idempotency_key ON payments (idempotency_key);
```

Derived from `Payment` entity (id, userId, amount numeric(38,2), currency, status, referenceId, idempotencyKey @Column(unique=true), createdAt).

### ledger-service (`src/main/resources/db/migration/V1__init.sql`)

```sql
CREATE TABLE ledger_entries (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  account_id BIGINT,
  payment_id BIGINT,
  loan_id BIGINT,
  amount NUMERIC(38, 2),
  currency VARCHAR(255),
  type VARCHAR(255),
  created_at TIMESTAMP
);

CREATE TABLE processed_events (
  event_id VARCHAR(255) PRIMARY KEY,
  processed_at TIMESTAMP
);

CREATE TABLE failed_events (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  event_id VARCHAR(255),
  event_type VARCHAR(255),
  payload TEXT,
  error_message VARCHAR(255),
  created_at TIMESTAMP
);
```

Derived from `LedgerEntry`, `ProcessedEvent`, `FailedEvent` (payload @Lob → TEXT in Postgres, H2 maps @Lob to TEXT).

### loan-service (`src/main/resources/db/migration/V1__init.sql`)

```sql
CREATE TABLE loans (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id BIGINT,
  amount NUMERIC(38, 2),
  currency VARCHAR(255),
  term_months INTEGER,
  status VARCHAR(255),
  created_at TIMESTAMP
);
```

Derived from `Loan` entity.

## Configuration changes

### Dependencies (per service `pom.xml`)

```xml
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-database-postgresql</artifactId>
  <scope>runtime</scope>
</dependency>
```

Version managed by Spring Boot BOM (flyway 10.x/11.x compatible with Boot 4).

### Main application.yml (per service)

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
  flyway:
    baseline-on-migrate: true
```

### Test application.yml (per service — replaces main entirely)

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
  flyway:
    baseline-on-migrate: true
  # ... existing Kafka/H2/JWT config unchanged
```

Note: test yml **replaces** main yml on the test classpath; all Flyway properties must be repeated (the documented gotcha in AGENTS.md).

## Existing databases

`baseline-on-migrate: true` with default `baseline-version: 1` handles all cases:

- **Existing dev DBs** (created by `ddl-auto: update`): Flyway inserts a baseline marker at version 1, skips V1. `validate` runs against the current schema — if V1's DDL matches Hibernate's output, no error. (The V1 DDL is derived from Hibernate's own output, so it matches.)
- **Fresh DBs** (CI `psql CREATE DATABASE`, new compose volumes): V1 runs, creates schema from scratch.
- **Empty test H2**: V1 runs, creates schema for tests.

## Testing

- All existing suites run against the Flyway-migrated schema (payment 7, ledger 3, loan 5 tests).
- `LoanEventHandlerIdempotencyTest` and `LedgerEventHandlerIdempotencyTest` exercise the 23505 unique-constraint skip on the V1-created unique index on `payments.idempotency_key` and `processed_events.event_id` PK.
- H2 `MODE=PostgreSQL` executes the same V1 scripts; `GENERATED BY DEFAULT AS IDENTITY` and `NUMERIC(38,2)` work identically on both engines.

## Landing

Single branch `feat/flyway-migrations` stacked on `feat/loan-service` (loan-service exists only there). One coherent PR per repo convention.

CI (`maven.yml`), docker-compose, and k8s need no changes — Flyway migrates on Spring Boot startup.

## Rollback

Flyway does not support down-migrations. To revert, drop the schema and re-run from an earlier baseline, or write a compensating forward migration. This is Flyway's philosophy.

## Open decisions (intentionally deferred)

- Multi-environment migration sets (dev vs prod) — not needed yet.
- Seed/reference data migrations — not in scope.
- flyway clean / repair commands — available but not automated.
